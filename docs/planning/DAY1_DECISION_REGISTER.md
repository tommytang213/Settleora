# Day 1 Decision Register

## Purpose

This register records explicit Day 1 product scope decisions that affect backlog generation, planning rows, manual gates, and Figma/reference needs. It complements [Day 1 execution coverage matrix](DAY1_EXECUTION_COVERAGE_MATRIX.md) and should be checked before generating missing or expanded GitHub issue candidates.

## Decisions

| D1-DEC-SCOPE-001 | PRD V5 versus MVP Day 1 conflicts are resolved row by row. Do not globally treat PRD V5 as always overriding MVP Day 1. Do not globally treat MVP Day 1 as always narrowing PRD V5. | Planning rule for Day 1 backlog generation | The source docs intentionally carry both broader PRD direction and narrower MVP Day 1 guardrails. A global rule would either silently over-promote future scope or incorrectly narrow explicit product decisions. | Ambiguous or risky rows must stay or become `Needs Decision` until explicitly resolved. If ambiguity affects money, auth, storage, privacy, trust, shared-user fairness, confusing UX, public/admin exposure, sync authority, or Day 1/2/3 scope, default to `Needs Decision`, not implementation. Harmless docs/UI-label polish may use the safer Day 1 interpretation when clearly non-risky. | D1-DEC-AUTH-001 | Day 1 complete includes passkeys/WebAuthn, TOTP authenticator-app MFA, recovery codes, admin/security policy controls for MFA/passkey availability and enforcement, and audit events for enrollment, removal, challenge success/failure, recovery-code generation/use/regeneration where safe, and policy changes. Do not store raw MFA secrets, passkey private material, recovery codes, reusable challenge material, raw reset tokens, raw session tokens, or raw provider tokens in unsafe tables, logs, API responses, generated clients, or audit metadata. Require explicit schema/API/OpenAPI/generated-client/UI issue breakdown before runtime work. | Generate Day 1 missing/partial issue candidates for passkey/WebAuthn, TOTP MFA, recovery codes, policy controls, audit, UI, and QA after this docs task. Do not generate those issues in this task. | Manual auth/security gate required. Figma/reference required for UI-sensitive enrollment, challenge, recovery, policy, and settings flows. |
| D1-DEC-AUTH-002 | Day 1 account creation supports first-owner bootstrap, admin-created users, invitation flow, public self-registration toggle, local accounts, and OIDC/Keycloak-compatible account flow where configured. | Day 1 | Self-hosted deployments need safe setup and onboarding options without making public registration the default. | Public self-registration is off by default but must be easy for non-technical self-hosted admins to enable intentionally from admin/settings with clear warnings and audit. OIDC/Keycloak remains configurable and must not store raw provider tokens in ordinary auth/profile tables. | Expand auth onboarding issue candidates to cover bootstrap, admin-created users, invitations, registration policy, local-account policy, OIDC/Keycloak configuration, warnings, and audit. Do not generate those issues in this task. | Manual auth/security gate required. Figma/reference required for onboarding, invitation, registration-policy, and admin settings UI. |
| D1-DEC-SHARING-001 | Day 1 includes friends/direct sharing. Direct bill sharing is allowed only between approved friends or through approved group/shared context. Temporary participants can later link/claim to real accounts while preserving historical participation. | Day 1 | PRD V5 requires approved friend relationships for direct sharing, and Day 1 trust depends on explicit sharing authorization rather than only group containers. | Server/admin policy should configure user discovery mode, exact-match requirement, global directory disabled/enabled state, friend-request approval, direct sharing permission rules, block/unfriend behavior, and payment-detail exposure rules. Safe defaults: exact-match discovery only, friend approval required before direct sharing, no browse-all-users directory, unfriend stops future sharing but preserves historical financial/audit records, and block stops requests, messages/comments where applicable, and future direct sharing. Payment details remain settlement/payment-context scoped by default; friend status alone does not expose payment details or QR files. | Generate missing Day 1 issue candidates for friends, direct sharing, discovery policy, approval, block/unfriend, temporary participant claim/link, and payment-detail exposure guardrails after this docs task. Do not generate those issues in this task. | Manual auth/security and privacy gates required. Figma/reference required for discovery, friend request, approval, block/unfriend, direct-share selection, and visibility flows. |
| D1-DEC-NOTIF-001 | Day 1 includes in-app notifications, email notifications via SMTP configuration, mobile push notification provider abstraction, device token registration/revocation/lifecycle handling, admin-level channel/provider policy, user-level preferences under admin policy, quiet hours, digest/immediate options, per-event category preferences, and group mute. | Day 1 | Day 1 collaboration and security workflows require notification trust across in-app, mobile, and email channels, while preferences prevent unwanted delivery. | Preference resolution: admin/system policy is the hard cap; user preference can narrow or select allowed channels but cannot enable a disabled channel; group mute/preferences can further reduce group-related notifications where policy allows. Security-critical events may bypass ordinary mute/digest rules only where security policy explicitly says so and audit/docs explain it. If email or push is unconfigured, UI/API must show unsupported or unconfigured state rather than pretending delivery succeeded. Notification content must remain privacy-safe. | Generate Day 1 issue candidates for SMTP/provider configuration, push abstraction, device-token lifecycle, channel policies, preferences, quiet hours, digest/immediate options, event categories, group mute, delivery states, and QA after this docs task. Do not generate those issues in this task. | Manual gate required for push/provider credentials, release/provider setup, and security-relevant notification delivery. Figma/reference required for preferences, channel state, permission, and delivery status UI. |
| D1-DEC-UXMODE-001 | Day 1 first launch should present `basic`, `advanced`, `guided`, and `help_me_decide`. Manual gates apply if implementation touches auth/security, money, storage, schema, OpenAPI, generated clients, or other gated domains. |

| D1-DEC-LOCAL-001 | Day 1 local mode security is user-configurable and should support app PIN where feasible, biometric unlock where platform supports it, encrypted local storage where feasible, encrypted local backup/export where feasible, clear no-collaboration warning, and later security-setting changes. | Day 1 | Local mode is a first-class Day 1 use path but has a different authority boundary from server collaboration. | Local mode security settings must not silently convert local-only data into server-mode account data.
