# Day 1 Decision Register

## Purpose

This register records explicit Day 1 product scope decisions that affect backlog generation, planning rows, manual gates, and Figma/reference needs. It complements [Day 1 execution coverage matrix](DAY1_EXECUTION_COVERAGE_MATRIX.md) and should be checked before generating missing or expanded GitHub issue candidates.

## Decisions

| Decision ID | Decision | Day scope | Rationale | Implementation gating notes | Issue-generation effect | Manual gate / Figma gate status |
|---|---|---|---|---|---|---|
| D1-DEC-AUTH-001 | Day 1 includes production-shaped passkey and MFA support. This is not only a future foundation. | Day 1 | Security and trust are core Day 1 product requirements, and PRD V5 explicitly includes passkey and MFA policy direction. | Must remain auth/security manual-gated. Do not store passkey private material, MFA secrets, raw recovery codes, raw reset tokens, raw session tokens, or raw provider tokens in unsafe tables, logs, or API responses. Require explicit schema/API/OpenAPI/generated-client/UI issue breakdown before implementation. If method details are not already settled, create decision issues rather than Codex inventing them. Day 1 minimum must avoid unsafe shortcuts such as SMS-only MFA, fake passkey UI, or client-only enforcement. | Generate Day 1 missing/partial issue candidates for passkey/MFA schema, policy, runtime, UI, recovery, and audit after this docs task. Do not generate those issues in this task. | Manual auth/security gate required. Figma/reference required for UI-sensitive enrollment, challenge, recovery, and settings flows. |
| D1-DEC-SHARING-001 | Day 1 includes approved friend requests and direct sharing. Direct sharing requires an approved friend relationship. Group-first sharing remains supported, but it is not the only Day 1 sharing model. Minimal temporary participants remain Day 1 for practical receipt capture where a person is not registered yet. | Day 1 | PRD V5 requires approved friend relationships for direct sharing, and Day 1 trust depends on explicit sharing authorization rather than only group containers. | Must remain auth/security and privacy manual-gated. No global user directory by default. Direct sharing authorization must be API-enforced. Payment details must not become globally visible through friend or direct-sharing work. Friend request lifecycle requires audit and notification coverage. | Generate missing Day 1 issue candidates for friends and direct sharing after this docs task. Do not generate those issues in this task. | Manual auth/security and privacy gates required. Figma/reference required for friend request, approval, direct-share selection, and visibility flows. |
| D1-DEC-NOTIF-001 | Day 1 includes in-app, mobile push, and email notification channels. Channel preferences are Day 1 where required to avoid sending unwanted notifications. | Day 1 | Day 1 collaboration and security workflows require notification trust across in-app, mobile, and email channels, while preferences prevent unwanted delivery. | In-app remains baseline. Email should use explicit self-hosted/admin-configured provider settings, likely SMTP or a provider abstraction. Push should use explicit mobile push provider/device-token architecture; do not fake push delivery with local-only UI labels. If a deployment has not configured email or push, UI/API must show unsupported or unconfigured state rather than silently dropping or pretending delivery succeeded. Include notification event taxonomy, channel preference enforcement, audit where security-relevant, and privacy-safe message content. Mobile push and release/provider credentials remain manual-gated. | Generate Day 1 issue candidates for email/push provider foundations, device tokens, preferences, delivery states, and QA after this docs task. Do not generate those issues in this task. | Manual gate required for mobile push, provider credentials, release/provider setup, and security-relevant notification delivery. Figma/reference required for preferences, channel state, permission, and delivery status UI. |
| D1-DEC-SCOPE-001 | PRD V5 versus MVP Day 1 conflicts are resolved row by row. Do not globally treat PRD V5 as always overriding MVP Day 1. Do not globally treat MVP Day 1 as always narrowing PRD V5. | Planning rule for Day 1 backlog generation | The source docs intentionally carry both broader PRD direction and narrower MVP Day 1 guardrails. A global rule would either silently over-promote future scope or incorrectly narrow explicit product decisions. | Default row-by-row rule: if Tommy explicitly promotes a broader PRD V5 item to Day 1, mark it Day 1 and require appropriate risk gates. If a broader PRD V5 item affects money, privacy, security, trust, shared-user fairness, storage/file authz, auth/session, confusing UX, or Day 1/2/3 scope and Tommy has not decided it, keep it `Needs Decision`. If a broader PRD V5 item is clearly Day 2/Day 3 in dedicated scope docs and Tommy has not promoted it, keep it deferred. If a narrow MVP Day 1 rule conflicts with a broader PRD V5 line, document the chosen row-level decision in this register or matrix notes. | Missing issue generation must use this decision register and must not silently promote every PRD V5 item. | No runtime manual gate for the planning rule itself. Manual gates still apply to each affected implementation row. |
| D1-DEC-UXMODE-001 | Day 1 includes Basic/Advanced or Simple/Advanced experience mode support. A Guided/Recommended mode may be included if existing docs support it, but do not invent a giant customization system. Users should be able to change the mode later. Where feasible, allow users to enable 1-2 advanced feature areas without accepting every advanced feature. | Day 1 | Day 1 usability needs approachable defaults without hiding required review states or changing backend authority. Existing UX architecture already defines simple/guided/advanced visibility concepts. | Experience mode controls UI visibility and workflow depth only. It must not alter backend authority, money calculations, authorization, storage access, audit, settlement state, or sync truth. Required review states, conflicts, security warnings, and money-impacting approvals must always surface even in Basic/Simple mode. Full drag-drop widget builders, full dashboard customization, and complex per-user product builders remain later unless already approved elsewhere. UI-sensitive implementation needs Figma/reference first. | Add a Day 1 coverage row if the matrix does not already capture this. Generate Day 1 issue candidates after this docs task. Do not generate those issues in this task. | Figma/reference required for UI-sensitive mode selection and visibility behavior. Manual gates apply if implementation touches auth/security, money, storage, schema, OpenAPI, generated clients, or other gated domains. |
