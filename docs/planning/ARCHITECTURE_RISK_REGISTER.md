# Architecture Risk Register

## Purpose

This register tracks production-dangerous architecture limitations that must not be hidden inside broad feature work. It records architecture and product safety decisions only; it does not mark runtime, schema, API, generated-client, UI, deployment, OCR, restore, retention, purge, web, or admin implementation complete.

Future branches should update this register when a high-risk limitation is discovered, when a safe next slice is completed, or when a manual gate changes the stop condition.

## Current Risk Register

| Area | Current limitation or risk | Future feature affected | Refactor risk | Production data risk | Required gate | Safe next slice | Stop condition |
| --- | --- | --- | --- | --- | --- | --- | --- |
| OCR review-first / no OCR-as-truth | OCR review/apply foundations exist, but OCR engine, worker, native capture, full classification, and non-draft revision apply remain incomplete. OCR output is candidate data only. | Receipt capture, OCR worker, mobile OCR, bill item creation, bill revision apply. | OCR confidence or worker completion could be mistaken for bill truth if future code bypasses review and API/domain validation. | Incorrect merchant, currency, totals, tax, refund, payer, split, or settlement state could become authoritative. | Product/OCR review, money validation, storage/privacy, API/domain validation, OpenAPI/generated-client if contracts change. | Keep all OCR output in candidate/review state; require user review/edit, apply preview, explicit apply, and API/domain validation before accepted bill state. | Stop if OCR completion, queue visibility, preview success, worker output, assignment state, or generated-client availability would finalize or mutate authoritative bills automatically. |
| Restore/import preview before apply | Restore/import architecture is staged, but full runtime restore/apply is not complete. | Local backup restore, CSV import, local-to-server migration, server-to-local re-import, user-web backup restore. | Parser or import session code could write before producing a reviewable diff. | Current local/server records could be overwritten, duplicated, erased, or linked to unsafe files. | Import/export/restore architecture, storage/privacy, money, auth/session, schema/OpenAPI/generated-client where runtime changes. | Implement non-mutating preview/diff with counts, conflicts, blocked sections, file inclusion status, and explicit confirmation before writes. | Stop if a restore/import path can write, replace, purge, clear conflict markers, or relink files before a user-visible preview and explicit apply. |
| Soft-delete / trash / purge separation | Some runtime slices have archive/remove foundations, but product-wide lifecycle and purge policy are not complete. | Bills, attachments, groups, memberships, payment details, sessions, notifications, imports/exports, audit, storage cleanup. | A generic delete abstraction could physically remove financial or shared history. | Loss of bills, splits, payer records, audit evidence, file metadata, shared participant history, or retention-required tombstones. | Retention/product policy, storage/privacy, audit, money/settlement, schema/migration before lifecycle fields change. | Document and implement lifecycle/status fields with timestamps, actor, reason, row version, restore, and separate purge controls per domain. | Stop if ordinary user-facing delete would hard-delete financial, shared, security, storage, sync, notification, import/export, or audit-related records. |
| Money/split/tax/refund/FX validation matrix | Current calculation evidence is partial; full Day 1 mixed tax, refund, fee, discount, FX, quantity-claim, and rounding matrix is not proven. | Bill creation/editing, OCR apply, import, recurring draft generation, revisions, settlement balances. | Later features may duplicate calculations in clients or workers instead of centralizing API/domain authority. | Wrong participant shares, tax allocation, refunds, FX snapshots, residuals, or settlement balances. | Money architecture/manual review, API/domain validation, focused test matrix, schema/OpenAPI if persisted shape changes. | Add focused API/domain validation matrix before widening bill/OCR/import/recurring acceptance. | Stop if clients, imports, OCR, or generated clients decide authoritative money, rounding, tax, refund, split, payer, or FX truth. |
| Sync/offline idempotency and conflict preservation | Offline queue and sync conflict foundations are partial; full cache hydration and conflict UI remain incomplete. | Offline shared edits, local-to-server migration, import retry, mobile queue replay, conflict notifications. | Retrying queued/imported work could duplicate accepted records or discard pending local edits. | Data loss, duplicate bills, stale overwrites, missing conflict evidence, or unauthorized acceptance. | Sync/idempotency architecture, API/domain validation, OpenAPI/generated-client and schema gates for runtime changes. | Preserve pending local candidates, use stable idempotency keys and conflict families, and return reviewable outcomes. | Stop if a retry, reconnect, sign-in, restore, or import silently overwrites, discards, or accepts pending/conflicted data. |
| Privacy vault runtime encryption handoff | Recoverable Private Vault is architecture direction; full runtime encryption, key rotation, envelope recovery, and admin policy are not complete. | Sensitive fields/files, backups, export/import, restore, payment details, OCR text, private notes, settlement proofs. | Vault work could move money or authorization authority to clients or drop metadata needed for recovery warnings. | Privacy downgrade, unrecoverable encrypted content, leaked sensitive metadata, or silent plaintext fallback. | Storage/privacy/security manual gate, vault architecture, backup/restore no-downgrade review, schema/API gates for runtime. | Implement narrow vault payload category with no-silent-downgrade warnings, redacted audit, and recovery-state preview. | Stop if a change stores raw keys/secrets, silently decrypts to plaintext, weakens vault policy, or makes clients authoritative for shared financial truth. |
| Deployment/migration/rollback production safety | Self-hosting and migration runbooks exist, but production-grade backup/restore evidence, destructive migration policy, and rollback proof remain incomplete. | TrueNAS install/upgrade, migrations, self-hosted deployments, storage volumes, backups, catalog packaging. | Broad deployment changes could alter persistence, env, ports, or migration behavior without operator review. | Data loss, failed upgrade, unsafe destructive migration, secret exposure, or unrollbackable deployment state. | Deployment/manual gate, migration safety review, Docker/CI validation, backup/restore runbook evidence. | Keep migration modes explicit, validate safe migrations separately, and require operator-visible evidence for restore/rollback. | Stop if deployment, Docker/env, CI, migration, destructive data operation, or production exposure changes are bundled into feature work without explicit gate. |
| Web/admin placeholder gap | User web and admin web remain placeholders while Day 1 scope requires full surfaces. | User portal, admin policy, audit viewer, backup/restore, import/export, security settings, provider settings. | Backend contracts may be shaped only for mobile starter flows and miss web/admin review needs. | Admin exposure, policy mutation, audit, restore, and security operations may ship without usable review/control surfaces. | Figma/reference for UI-sensitive work, admin/security/manual gates, OpenAPI/generated-client where contracts change. | Split user-web/admin feature slices by domain with safe read-only foundations before mutation surfaces. | Stop if web/admin UI claims Day 1 completion, exposes admin/public surfaces, or mutates security/storage/money policy without reviewed runtime/API gates. |
